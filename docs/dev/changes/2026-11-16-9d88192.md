# deploy.sh refreshes .env from SSM Parameter Store

- **Date:** 2026-11-16
- **Branch:** feature/autonomous-course-create
- **Commits:** 99c748d..9d88192

## What changed
- `deploy.sh` now reads the SSM SecureString parameter `/kse-notes/env` and writes it to `.env` before rebuilding the containers.
- The parameter name can be overridden with the `ENV_PARAMETER` variable.
- The file is written with `umask 077` to `.env.new`, then moved over `.env`, so `.env` is mode 600 and is never half-written.
- The README's Secrets paragraph now says secrets live in SSM, not hand-edited on the instance.

## Why
Not stated. Probably to keep secrets in one managed place instead of a file edited on the instance.

## Where
- [deploy.sh](../../scripts/aws/deploy.sh): fetches the parameter with `aws ssm get-parameter --with-decryption`.
- [README.md](../../README.md): AWS section, Secrets bullet.

## API and data
Env: `ENV_PARAMETER` (optional, default `/kse-notes/env`). The parameter holds the `.env` contents. No endpoint or table changes.

## How to try it / migrate
- Create the SecureString parameter `/kse-notes/env` with the full `.env` contents.
- The instance role `kse-notes-ec2` needs `ssm:GetParameter` (and KMS decrypt if a custom key is used). The diff does not show this being granted.
- Run `sudo /opt/kse-notes/scripts/aws/deploy.sh`.

## Follow-ups
- Edits made directly to `/opt/kse-notes/.env` are overwritten on the next deploy.
- If the `aws` call fails, `.env.new` may be left behind; whether the script stops depends on its `set` options.
