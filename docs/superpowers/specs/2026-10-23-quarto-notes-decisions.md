# Доопрацювання конспектів через Quarto: ухвалені архітектурні рішення

Статус: реалізовано в гілці `feature/quarto-notes` (задачі P1.1–P3.1). Не реалізовано: P3.2 (книга курсу) та P3.3 (повне приймання); їхні рішення наведені в кінці як заплановані.

Цей документ доповнює [специфікацію](2026-10-22-quarto-notes.md). Специфікація описує мету й межі; тут записано обов'язкові рішення, які ухвалено під час виконання, і причини. Вони діяли як вимоги до задач і не мають зникнути разом з тимчасовими робочими нотатками. Якщо код розходиться з цим текстом, правильний код; розбіжність слід виправити в документі.

Кожне рішення записано так: що вирішено, чому, де в коді. Шляхи вказані відносно `api/app/`, якщо не сказано інше.

## Структура сховища

```
uploads/.worker.lock                     блокування життя єдиного працюючого worker
uploads/<course>/notes/<run>/
  notes.json                             початковий результат генерації: ревізія 0, незмінний
  .run.lock                              стабільний файл блокування run (ніколи не замінюється й не видаляється)
  head.json                              {"revision": N}: єдина точка фіксації ревізій >= 1
  assets/<sha256>.png|jpg                незмінні рисунки run
  revisions/000000/                      заморожений baseline 0 (створюється під час першого запису)
  revisions/NNNNNN/document.json         повний документ ревізії
  revisions/NNNNNN/revision.json         RevisionInfo: parent, origin, changed_topics, provenance
  revisions/NNNNNN/jobs/<job>.json       render jobs ревізії
  revisions/NNNNNN/artifacts/<job>/...   вихідні файли однієї job (незмінні)
  revisions/NNNNNN/artifacts/manifest.json
  revisions/NNNNNN/.render.lock          блокування рендерингу ревізії
  revisions/.staging-<uuid>/             незавершені знімки; ігноруються
  suggestions/<id>.json                  AI-пропозиції (поза знімками)
  verification-jobs/<id>.json            ручні перевірки (поза знімками)
```

## 1. Контрольований QMD і дозволений Markdown

- **Рішення.** `NotesDocument` лишається єдиним джерелом змісту; `.qmd` похідний і не редагується двобічно. Тіло блоку не може впроваджувати shortcodes Quarto (`{{< >}}`, `{{% %}}`), сирі атрибути, виконувані клітинки, YAML-метадані, сирий HTML, сирі TeX-команди підключення ресурсів (`\input`, `\includegraphics` тощо), небезпечні посилання (`javascript:`, `data:`, `file:`) та зображення, крім зареєстрованих. Звичайний відображуваний код (кодові блоки з простою назвою мови, `inline code`) і формули дозволені. Чинний вихідний текст ніколи не переписується, щоб виглядати допустимим: його відхиляють.
- **Рішення.** Конфігурація (YAML front matter) приймається лише у канонічному вигляді, який формує сервер; `validated_source` порівнює її з перебудованою і відхиляє будь-яку різницю, також під час повторного рендерингу. Використовується markdown-вхід `-raw_html-raw_tex-raw_attribute-yaml_metadata_block`, `execute: enabled: false` і `--no-execute`.
- **Рішення.** Кожен формат будується в окремому тимчасовому проєкті Quarto з власним `_quarto.yml` (`project: type: default`), щоб Quarto не знаходив конфігурацію, розширення чи метадані вище за каталогом. Команди запускаються списком аргументів без shell, у новій групі процесів; після тайм-ауту (600 с) група знищується, а процес завершується й збирається.
- **Чому.** Лише `--no-execute` не ізолює: shortcodes, include і raw-вставки читають довільні ресурси. Недокументований прапорець `--no-project` не використовується.
- **Де.** `worker/quarto.py` (`validate_markdown`, `validated_source`, `render_document`); `worker/render.py` (`front_matter`).

## 2. Окремі джерела для кожного формату; `typst_safe` лише для PDF

- **Рішення.** Для HTML, PDF і DOCX готуються окремі QMD-джерела, і кожен рендериться незалежно. Перетворення формул для Typst (`typst_safe`, `clean_math`) застосовується тільки до цілі `pdf`; HTML (MathJax) і Word отримують формули без змін. `RenderFormat = Literal['html','pdf','docx']`; PDF мапиться на `--to typst`. Збій одного формату не знімає успішних інших.
- **Чому.** Виправлення для Pandoc/Typst спотворюють формули в інших виходах. Спільні моделі живуть у `app/notes.py`, щоб API не залежав від коду worker.
- **Де.** `worker/render.py` (`typst_safe`, `to_quarto(..., target)`, `topic_to_quarto`); `worker/quarto.py` (`render_document`); `notes.py` (`RenderFormat`, `RenderedArtifact`).

## 3. Ізоляція HTML-перегляду

- **Рішення.** HTML віддається із заголовком `Content-Security-Policy: sandbox allow-scripts; default-src 'none'; ...` (скрипти лише inline і MathJax з `cdn.jsdelivr.net/npm/mathjax@3/`, `connect-src 'none'`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`. У застосунку HTML відкривається в `iframe` з `sandbox="allow-scripts"` (без `allow-same-origin`). Заголовок діє й при прямому відкритті адреси, тому cookie та сховище застосунку недоступні.
- **Чому.** Згенерований HTML не повинен мати доступу до стану застосунку; одного атрибута iframe недостатньо для прямого відкриття. Повністю автономний HTML без мережі не обіцяється: MathJax береться з CDN.
- **Де.** `routers/notes.py` (`HTML_HEADERS`); `web/src/components/preview/notes-preview.tsx`.

## 4. Посилання: PUBLIC_API_URL і прив'язка до ревізії

- **Рішення.** Бібліографія (`citeproc: true`) будується зі списку CSL JSON із ключами `src-{Source.id}` і полями `id`, `type`, `title`: автори, роки й сторінки не вигадуються. Сторінка в цитуванні береться з надрукованого номера доказу (`[@src-1, p. 10]`), не зі зсуву PDF. Мітки формул, таблиць і рисунків мають префікси `eq-`, `tbl-`, `fig-`; їх коректність і унікальність перевіряються перед рендерингом (`validate_references`). Якорі тем і блоків (`sec-...`) кодуються оборотно від ID, тому не змінюються після правки заголовка.
- **Рішення.** Для автономних PDF і DOCX міжтемні посилання абсолютні. Базу задає довірена конфігурація `PUBLIC_API_URL` (за замовчуванням `http://localhost:8000`, є в API і worker та в `.env.example`): лише HTTP(S), без облікових даних, query і fragment, з підтримкою префікса шляху розгортання. Заголовок `Host` запиту ніколи не використовується. Компоненти маршруту (course, run, topic) кодуються у відсотках.
- **Рішення.** Рендеринг ревізії N посилається на `.../revisions/N/artifacts/html`, а не на застарілий псевдонім `.../html`, який вказує на найновішу ревізію. Генерація (ревізія 0) теж посилається на `/revisions/0/artifacts/html`.
- **Чому.** Автономний файл не повинен непомітно вести читача до новішого тексту. Контекст посилань (`ReferenceContext`) передається в форматувальник явно, а не зашивається.
- **Де.** `config.py` (`validate_public_api_url`, `Settings.public_api_url`); `worker/config.py`; `worker/references.py` (`build_reference_data`, `reference_id`, `validate_references`, `normalize_links`, `ReferenceContext`, `revision_context`); `worker/notes.py` (генерація використовує `revision_context(..., 0)`).
- **Українські підписи.** Quarto 1.10.19 не застосовує переклад `ua` до мови `uk`, тому для `uk` явно задаються `toc-title`, підписи «Рисунок», «Таблиця», «Розділ», «Рівняння» та заголовок розділу джерел; для `en` лишаються англійські. Збережена мова документа не змінюється. `worker/render.py` (`front_matter`, `LABELS`).

## 5. Імпорт рисунків і реєстр ресурсів

- **Рішення.** Рисунки приймаються лише як PNG/JPEG через `POST /plans/{course}/notes/{run}/assets` (multipart). Зображення канонізується через Pillow: до 10 МіБ і 20 млн декодованих пікселів, пошкоджені, обрізані й непідтримувані файли (зокрема SVG) відхиляються. Файл зберігається як `assets/<sha256>.png|jpg` з незмінним вмістом; інший вміст за тією ж назвою ніколи не перезаписує існуючий. Вивантаження лише зберігає файл і запис каталогу й **не змінює жодної ревізії**. Історичні ресурси не видаляються.
- **Рішення.** У тексті дозволено лише рядкову форму `![підпис](assets/<sha256>.png){#fig-мітка}` з підписом і міткою `fig-`. `NotesDocument.assets` (`NoteAsset`: id, name, path, media_type, sha256, width, height) є реєстром документа. Під час збереження теми кожне посилання перевіряється за каталогом цього run (невідомий шлях, шлях іншого run, неправильне розширення, небезпечний синтаксис дають 422), і нові ресурси додаються до реєстру ревізії; реєстр лише розширюється, тож посилання незмінених тем переживають ревізії й restore.
- **Рішення.** Рендерер копіює в тимчасовий проєкт лише ті ресурси, на які формат справді посилається, і на межі процесу ще раз перевіряє корінь каталогу, ім'я за хешем, відсутність symlink і збіг sha256. Віддалені URL, автоматична генерація діаграм і витягання зображень із PDF не підтримуються.
- **Де.** `note_assets.py` (`import_asset`, `image_references`, `asset_resources`); `notes_revisions.py` (`register_figures`); `worker/quarto.py` (`render_document`, `resources`); `routers/notes.py` (маршрути assets); у UI вставка в чернетку блоку, `web/src/components/notes/editor.tsx`.

## 6. Мова старих документів: без вгадування, лише явний вибір

- **Рішення.** `NotesDocument.language` може бути `None`. Для старих документів (`schema_version == 1`) мову лише читають без запису з основного transcript курсу, якщо він доступний; помилки читання (зокрема недійсний UTF-8) дають `None`. Інакше мова лишається невідомою.
- **Рішення.** Рендеринг ревізії з `language is None` не вгадує англійську: job одразу стає `failed` з вказівкою вибрати українську чи англійську в редакторі, жодного виклику CLI чи LLM, текст і попередні файли збережені.
- **Рішення.** `TopicPatch.language` (`uk`|`en`) може заповнити невідому мову або повторити збережену; конфлікт зі збереженою мовою дає 422 (переклад не входить в обсяг). Лише-мовна ініціалізація створює ручну ревізію з `changed_topics=[]`, зберігає перевірки тем і не є no-op. Редактор показує явний вибір мови й не дозволяє зберегти без нього.
- **Де.** `notes.py` (`load_document`, `legacy_language`); `notes_revisions.py` (`TopicPatch.language`, `commit_topic`); `worker/revisions.py` (`render_job`).

## 7. Заморожена ревізія 0 і відмова resume для опублікованого run

- **Рішення.** Початковий `notes.json` є ревізією 0 і ніколи не переписується. Після публікації завершеного документа ревізія 0 заморожена: `POST /plans/{course}/notes` з `resume` для run зі статусом `done` або з каталогом `revisions/` відхиляється з 409 і порадою створити новий run або перерендерити. Невдалий, ще не опублікований run продовжує бути придатним до resume. Ручні правки ніколи не перезаписуються resume.
- **Чому.** Інакше resume переписав би `notes.json` після рендерингу ревізії 0 і зіпсував би історію. Перевірка лише в endpoint ревізій не закриває гонку з `open_run`.
- **Де.** `worker/notes.py` (`open_run`, `COMPLETED_RUN`); UI: кнопка «Resume» лишається тільки для невдалих run, `web/src/components/dashboard/notes-stage.tsx`.

## 8. Спільне блокування run, HEAD як єдина точка фіксації

- **Рішення.** Усі зміни ревізій, допуск генерації/resume, переходи станів пропозицій і ручних перевірок проходять під одним стабільним файлом `.run.lock` через `fcntl.flock` (macOS/Linux). Блокування коротке й ніколи не тримається під час `await`, LLM чи рендерингу. Асинхронні виклики беруть його в потоці (`asyncio.to_thread`), щоб не блокувати цикл подій. Редагувати можна лише run у стані `done`; усі інші стани (`queued`, `running`, `failed`) дають 409.
- **Рішення (протокол запису).** Під блокуванням: перевірити `done`; один раз прочитати HEAD; перевірити `base_revision` (інакше 409 «Revision changed; current revision is N»); глибоко скопіювати документ; перевірити область, ID, докази й рисунки; якщо змін немає, повернути поточну ревізію без нової (no-op); записати знімок у `.staging-<uuid>` і перейменувати каталог на місце; атомарно замінити `head.json` (`os.replace` з унікального `.head-<uuid>`). **Заміна HEAD — єдина точка фіксації.** Номер виділяється вище за всі наявні числові каталоги, включно з осиротілими; прогалини допустимі.
- **Рішення (orphans).** Каталог, перейменований без наступної заміни HEAD, є прихованим orphan: його не показують, не приймають автоматично й не перезаписують. Історія й читання явної ревізії доступні лише для HEAD і ланцюга `parent` (плюс віртуальна ревізія 0); цикл або порушений порядок дає помилку. Читачі нічого не пишуть і читають HEAD один раз на запит.
- **Рішення (baseline 0).** Перший запис один раз матеріалізує `revisions/000000` з поточного вигляду ревізії 0 (з відновленою мовою старого документа) атомарним перейменуванням каталогу; це вузька ініціалізація, а не редакційний orphan. Наявний валідний `000000` зберігається, навіть якщо `head.json` ще немає. Пошкоджені або неузгоджені з `notes.json` метадані baseline відхиляються (409) і не перезаписуються; читачі тоді повертаються до віртуальної ревізії 0.
- **Чому.** Перейменування каталогу й заміна HEAD — дві операції; між ними можливий збій. Тестується завершення процесу перед перейменуванням, після нього й після заміни HEAD, а також гонки edit/edit і resume/edit у різних процесах. Заява про довговічність при втраті живлення не робиться: перейменування лише забезпечує видимість.
- **Де.** `notes_revisions.py` (`run_lock`, `RevisionStore.transaction/commit/_publish/_allocate/_baseline/_history`, `commit_topic`).

## 9. Restore і втрата актуальності перевірки

- **Рішення.** Restore відновлює зміст, а не історичну перевірку. Для кожної теми порівнюються авторські поля (`title`, `objectives`, `blocks`, `evidence`) без метаданих перевірки. Змінена тема отримує зміст цільового знімка й стає `unresolved` з `verification_stale=true`, без `verifier`, без `rounds` і без блочних проблем. Незмінені теми зберігають **поточні** метадані перевірки, навіть якщо в цільовому знімку статус інший; `verified` ніколи не воскресає. Записуються `origin='restore'`, `parent=поточна`, `restored_from=ціль` і точний список `changed_topics`. HEAD завжди просувається вперед, історичні знімки не змінюються. Restore без змін повертає поточну ревізію без нової (no-op).
- **Рішення.** Одна функція `invalidate_verification` застосовується до ручних, AI та restore-змін: вона лишає тільки прогалини, які випливають із замороженої вибірки доказів, й заново обчислює детерміновані структурні прогалини з поточного тексту; результати верифікатора (блочні й тематичні) скидаються, бо стосувалися іншого тексту. Реальні прогалини лишаються видимими.
- **Де.** `notes_revisions.py` (`invalidate_verification`, `authored`, `RevisionStore.restore`); `note_structure.py` (`structure_gaps`, `evidence_gaps`, `topic_structure_issues`). Вимога навчальної структури (інтуїція, означення, приклад тощо) залежить від `TopicNote.objectives`; для старих тем без цілей порожній список не накладає шаблону. Синонім `overview` задовольняє ціль «інтуїція».

## 10. Render jobs

- **Рішення (намір до HEAD).** Початкова queued job (HTML+PDF) записується всередині підготовленого знімка ревізії **до** заміни HEAD і запускається після фіксації. Тому збій між фіксацією й плануванням не залишає ревізії без job. Збереження, restore, застосування AI-пропозиції та запис ручної перевірки повертають цю staged job; повторний пошук job після фіксації не виконується. Явний повторний рендеринг (`POST .../revisions/{revision}/render {formats}`) записує job до планування; допускається лише для run у стані `done`, а для ревізії 0 спершу заморожується baseline.
- **Рішення (незмінні виходи).** Кожна job пише у власний каталог `artifacts/<job-id>/`, а потім атомарно замінює `manifest.json`. Шлях, на який посилається чинний маніфест, ніколи не перезаписується. Шляхи маніфесту перевіряються на належність каталогу артефактів ревізії, нечитабельний маніфест вважається порожнім.
- **Рішення (злиття).** Під блокуванням рендерингу ревізії (`.render.lock`, неблокувальні проби `flock` з `asyncio.sleep`, щоб цикл подій і health не зависали) маніфест перечитується й зливається за ключем `(topic_id, format)`. Повторна невдача того ж ключа зберігає попередній готовий файл; помилка записується в job. Часткова невдача публікує успішні ключі, а job завершується `failed` зі списком помилок. Блокування run і рендерингу не вкладаються через `await`.
- **Рішення (читання).** Явні URL ревізії (`.../revisions/{n}/artifacts/{kind}`, `.../topics/{topic}/artifacts/{kind}`) канонічні й **ніколи не переходять на іншу ревізію** (404). Застарілі URL без ревізії є псевдонімами найновішого готового файлу й завжди повертають заголовок `X-Notes-Revision` з фактичною ревізією; QMD завжди ревізія 0. Резервний вибір виводиться із зафіксованих ревізій, а не з того, яка job закінчилася останньою. `display_revision` описує показаний артефакт, а не всі формати разом: HTML може бути новішим за PDF.
- **Рішення (область).** Рендеринг не викликає LLM, планувальник чи гармонізацію. Окремі файли тем будуються для тем зі статусом `verified` або `unresolved`. Стара job не змінює HEAD і не підміняє новіший артефакт.
- **UI.** Опитування прив'язане до job, а не до всього документа; відповіді впорядковані за послідовністю, тому запізніла відповідь з тією ж текстовою ревізією не повертає старий артефакт чи стан job. Старий файл завжди позначений номером його ревізії («Older artifact»); є Retry.
- **Де.** `worker/revisions.py` (`enqueue_render`, `render_revision`, `render_job`, `render_lock`); `notes_artifacts.py` (`manifest`, `selected_artifacts`, `artifact_path`, `atomic_json`); `routers/notes.py` (`view`, `served`, `latest_ready`, `revision_download`); `notes_revisions.py` (`_publish`); `web/src/components/preview/notes-preview.tsx`.

## 11. Відновлення при старті та блокування життя worker

- **Рішення.** Працювати може один обслуговуючий worker. На старті він бере неблокувальний `flock` на `uploads/.worker.lock` і тримає його весь час життя; другий процес зупиняється з помилкою «Another worker is already serving this uploads directory» ще до відновлення, тож не позначить чужу живу роботу невдалою.
- **Рішення.** Лише після цього виконується глобальне відновлення: перерваний run генерації, render jobs, AI-пропозиції та ручні перевірки зі станом `queued`/`running` стають `failed` з поясненням (render: «Worker restarted before rendering completed; retry this revision»). Готові, застосовані й відхилені пропозиції та зафіксовані артефакти не чіпаються. Розглядаються тільки зафіксовані ревізії; пошкоджений запис чи історія одного run логуються й пропускаються, не зупиняючи відновлення інших. Пропозиція чи перевірка, чия ревізія вже зафіксована (за provenance), зводиться до `applied`/`done`, а не до помилки. Повторна спроба створює нову роботу з явною ревізією.
- **Чому.** Жодна job не лишається в очікуванні назавжди; рендеринг повторюється без викликів LLM.
- **Де.** `worker/main.py` (`lifespan`); `worker/notes.py` (`fail_interrupted`); `worker/revisions.py` (`fail_interrupted_renders`); `worker/note_suggestions.py` (`fail_interrupted_jobs`, `recover_run`).

## 12. Спільна межа підпроцесів Quarto

- **Рішення.** Кількість одночасних підпроцесів Quarto обмежена налаштуванням `quarto_concurrency` (`QUARTO_CONCURRENCY`, за замовчуванням 4) і спільна для початкової генерації та всіх job ревізій у процесі worker: один `asyncio.Semaphore` на цикл подій. Семафор охоплює лише підпроцес; очікування слота асинхронне, а скасування звільняє слот. Окремого ліміту на кожну job немає.
- **Чому.** Інакше накладені рендеринги ревізій і run перевищили б пам'ять (безкоштовний інстанс має 512 МБ). Нової черги чи сервісу не вводиться.
- **Де.** `worker/quarto.py` (`subprocess_gate`, `render_document`); `worker/config.py`.

## 13. AI-пропозиції

- **Рішення.** AI створює пропозицію, а не змінює документ. Порожній `block_ids` означає всю тему; інші теми заборонені. Пропозиція зберігається окремо від знімків (`suggestions/<id>.json`) разом з приватними даними: областю (`block_ids`), інструкцією, заміною блоків, вставками з явним `after_block_id` (для обраної області обов'язковий вибраний блок-якір) та повним зібраним кандидатом (`proposed_blocks`). ID нових блоків призначає сервер до перевірки й перегляду; модель повертає лише структуровані заміни та вставки з номерами доказів.
- **Рішення.** Сервер сам перебудовує тему (`assemble`): незмінені блоки та їхній порядок зберігаються; відхиляються зміна блоків поза областю, дублікати ID, порожній текст, цитати поза замороженими доказами **цієї** теми, пропозиції без змін і кандидат, що додає нові проблеми посилань чи нереєстрований рисунок.
- **Рішення (apply).** Потрібно `request.base_revision == suggestion.base_revision == HEAD`; підроблена нова база дає 409, перебазування заборонене. Усе перевіряється заново в тій самій транзакції під блокуванням run, включно зі збігом збереженого кандидата з перебудованим. Переходи станів (`queued → running → ready → applied|rejected`, `failed`) захищені: запізніле завершення не може перетворити `rejected` на `ready`; apply і reject змагаються з одним результатом. Id пропозиції записується в `revision.json` застосованої ревізії; повторний apply (також після збою між фіксацією й оновленням статусу) повертає наявну ревізію й не створює другу.
- **Рішення (перевірка).** Нова перевірка прив'язана до відбитка (fingerprint, sha256) точного вмісту: упорядковані блоки, цитати, докази, реєстр позначень і контекст, які бачить верифікатор. Перевіряється повна зібрана тема. Якщо відбиток під час apply збігається, застосований текст може отримати результат перевірки; інакше тема лишається `unresolved` з `verification_stale`.
- **Рішення (`verified`, `blocking`).** `verified` ставиться лише коли перевірка чиста (немає major-проблем і немає ескалації) та в темі немає чинної прогалини доказів. Поле `NoteSuggestion.verified` (і `VerificationJob.verified`) обчислюється цим же правилом, що й apply, а `blocking` перелічує прогалини, через які тема не може стати `verified`. Структурні прогалини додаються до результату як major. Невизначена перевірка (`escalate`) ніколи не дає `verified`; відсутність доказів лишається `unresolved` з причиною.
- **Рішення (доступність).** Без OpenRouter лише AI-команди повертають 503; ручне редагування, рендеринг і restore працюють без нього (жодних викликів моделі).
- **Де.** `notes_suggestions.py` (моделі, сховище); `worker/note_suggestions.py` (`assemble`, `convert`, `check_candidate`, `fingerprint`, `is_clean`, `is_verified`, `certify`, `create_suggestion`, `run_suggestion`, `transition`, `apply_suggestion`, `reject_suggestion`); `routers/notes.py`; UI `web/src/components/notes/suggestion-review.tsx`. Нові схеми відповідей моделі додаються і в `answer()`, і в `SCHEMAS` (`api/tests/e2e/synthetic.py`).

## 14. Ручна повторна перевірка (`origin='verification'`)

- **Рішення.** Щоб відредагований вручну текст міг стати свіжо перевіреним без переписування AI, є `POST .../topics/{topic}/verify {base_revision}`, що створює збережену job (`queued → running → done|failed`), та `GET .../verification-jobs/{id}`. Існуючий верифікатор перевіряє заморожену повну тему з доказами й контекстом (разом із детермінованими прогалинами).
- **Рішення (завершення).** Під блокуванням run результат записується як нова незмінна метадані-ревізія з `origin='verification'` і `verification_job` (зміст не змінюється, готується рендеринг), лише якщо HEAD не змінився **і** відбиток поточної теми збігається. Інакше результат зберігається в job як `conflict` без змін HEAD: застаріла перевірка ніколи не сертифікує новіший текст. Невдала чи неоднозначна перевірка лишає тему `unresolved` з актуальними проблемами; скасування чи збій позначають job `failed`.
- **Де.** `worker/note_suggestions.py` (`create_verification`, `run_verification`, `record_verification`, `certify`); `notes_revisions.py` (`RevisionInfo.origin`, `verification_job`).

## 15. DOCX

- **Рішення.** Word створюється на вимогу, як додатковий формат тієї самої job (`formats:['docx']`), а не після кожного збереження; збереження, restore і apply просять лише HTML та PDF. DOCX обраної ревізії будується з того самого знімка командою `quarto render --to docx --no-execute`; збій DOCX не змінює готових HTML/PDF. Формули лишаються рідними OMML, цитування й бібліографія зберігаються; `typst_safe` не застосовується. Файл віддається як `attachment` з медіатипом Word і заголовком `X-Notes-Revision`.
- **Рішення (зміст).** Рідне поле TOC порожнє, поки читач не оновить його, тому для Word `toc: false`, а в документ записується статичний список змісту з посиланнями на явні якорі розділів (`{#section-N}`) і наявні якорі тем (`#sec-<topic>`); номери повторюють нумерацію заголовків Quarto. Окремий DOCX теми змісту не має.
- **Рішення (`polish_docx`).** Невелика обробка файлу, який записав Quarto: проміжок перед номером нумерованої формули стає звичайним текстом (інакше LibreOffice склеює «формула.(1)»), а рядкам-заголовкам callout додається `keepNext`, щоб заголовок не відривався від тіла. Для вбудованого `(x)^n` Pandoc розміщує в основі `m:sSup` лише закривальну дужку; LibreOffice Math показував `¿`. Обробка переносить наявні збалансовані прості OMML-руни дужкового виразу в основу `m:sSup`. Неврівноважені чи структурно неоднозначні вирази не змінюються; формули залишаються редагованим OMML. Не-ZIP результат вважається помилкою артефакту. Важка залежність офісу для оновлення полів не додається, `reference-doc` не вводиться.
- **Обмеження.** Зміст без номерів сторінок і статичний; високі callout переходять на наступну сторінку. Контрольний DOCX, перетворений справжнім LibreOffice Math на PDF, показує `(2-\lambda)^{2}` і `(1,1)^T` без `¿`; усі шість сторінок переглянуто. Той самий DOCX імпортовано до Google Docs через конектор: документ має 37 рівнянь, а PDF Google Docs Renderer також показує обидва степені без `¿` на сторінці 4. Імпорт Google Docs сплощує матриці в рядки й може розривати заголовок callout з тілом; оригінальний DOCX у LibreOffice зберігає матриці. У самому Microsoft Word і браузерному інтерфейсі Google Docs ще не перевірено.
- **UI.** Група «Word» у вкладці перегляду: `Prepare Word`, `Preparing Word…`, `Download Word` (лише для файлу рівно поточної ревізії), `Retry Word`; файл старішої ревізії показується лише приглушеним посиланням «Older Word file · revision N». У вкладці History обрана незмінна ревізія, включно з нульовою, має окремі підготовку, стан job, повторну спробу й посилання на її власний Word-артефакт; перемикання ревізії не підміняє файл.
- **Де.** `worker/render.py` (`word_contents`, `section_id`, `front_matter`); `worker/docx.py` (`polish_docx`); `worker/quarto.py`; `routers/notes.py`; `web/src/components/preview/notes-preview.tsx`; `web/src/components/notes/revision-history.tsx` і `revision-word.tsx`.

## Не реалізовано

### P3.2: книга курсу з пошуком

Задачу відкладено. Для неї обов'язкові рішення, ухвалені за результатами попереднього дослідження (Quarto 1.10.19, Chrome 155); вони заплановані, але не реалізовані:

- Нове значення `RenderFormat='book'` (каталог із входом `index.html`, окремий від standalone HTML); глави використовують формат `html`, а не `book`. Інтерфейси: `build_book_project(document, directory, language) -> Path`, `async render_book(directory, revision, quarto) -> RenderedArtifact`, `GET .../revisions/{revision}/book/{asset_path:path}`, `POST .../render` з `formats:['book']`; книга будується в окремому каталозі job і не зливається в маніфест як звичайний `html`.
- Одна незмінна ревізія будує всі глави, індекс пошуку й маніфест; невдала перебудова не замінює останній успішний артефакт. Назви файлів глав походять від ID тем (дублікати заголовків лишаються різними), порядок глав відповідає документу, відсутні чи невдалі теми мають видиму сторінку статусу, а не зникають. У пошук і публікацію не потрапляють підручники, чанки, промпти, QMD-джерела та проміжні AI-файли.
- Видача лише файлів із явного маніфесту публікації з перевіркою розв'язаного шляху (шлях через `..` і symlink назовні відхиляються), сервер ніколи не віддає каталог run чи staging. `book/` обслуговується як `index.html`, бо Quarto генерує `./`.
- Ізоляція: і HTTP CSP, і iframe мають рівно `sandbox allow-scripts` (без `allow-same-origin`); окрема для книги CSP із довіреною базою `BOOK_BASE` (походження з конфігурації `PUBLIC_API_URL`, не із заголовків), локальні стилі й шрифти (`theme: default`, без Google Fonts), серверний резерв `localStorage` у пам'яті лише після `SecurityError`. `Access-Control-Allow-Origin: *` лише для успішних опублікованих файлів книги; не додавати `null` і не змінювати загальну CORS-політику із credentials. Остаточні заголовки після middleware (`allow_credentials=True`) треба перевірити окремо.
- Міжтемні посилання в книзі ведуть до глави-власника в тій самій ревізії, а не до окремого повного HTML чи якоря індексу. Приймання: пошук українського терміна, перехід за результатом, між темами, до джерел, посилання previous/next, жодних помилок завантаження модулів, шрифтів чи пошуку, відсутність доступу до cookie/DOM/сховища батьківської сторінки.

### P3.3: повне інтеграційне приймання

Не виконано. Наявні: синтетична контрольна fixture (`api/tests/fixtures/notes`), ізольований стек і Playwright-набір `cd web && npm run test:e2e:notes` (див. `web/e2e/notes/README.md`), що покривають генерацію, редагування, 409, історію, restore, перерендеринг з реальним Quarto, AI-пропозиції, ручну перевірку та Word. Сценарій книги з пошуком лишається `test.fixme`. Контрольний DOCX оглянуто в LibreOffice Math на всіх шести сторінках. Ще не зроблено: повну візуальну перевірку HTML (390 px й desktop), усіх сторінок контрольного PDF, книгу та наскрізне приймання користувачем. Обов'язкові правила для цієї задачі: справжній Quarto замість підміни всіх job успіхом; відсутність браузера чи CLI не вважається проходженням; тестовий стек без виробничих ключів і даних.

## Відомі обмеження

- Довговічність при втраті живлення не заявляється (немає fsync каталогів і маніфесту).
- Одночасно обслуговує один worker; розподіленої черги немає.
- Опитування стану run і job читає історію ревізій при кожному запиті (вартість O(ревізій)); baseline 0 перечитується щоразу.
- AI-пропозиція існує лише в стані компонента й не показується після перезавантаження сторінки (запис лишається на диску, доступний через GET API, переліку немає).
- Word не перевірено в самому Microsoft Word. Імпорт у Google Docs перевірено через конектор та експортований PDF, з наведеними вище втратами форматування матриць і callout.
