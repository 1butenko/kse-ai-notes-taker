# P2.5 — Teacher approval of saved notes

Status: implemented and independently reviewed2026-10-26. Full native API478passed/3external-live skips, full browser22/22passed, lint and production build passed. User authorization supersedes prior planned-only status; existing Quarto notes spec/revision architecture remain binding.

## User behavior

Teacher can review current AI findings, approve a saved nonempty topic for students, and revoke that decision. Approval is separate from AI verification: it never changes status to verified, clears findings, or removes source/citation records. The teacher UI keeps AI status/findings and shows separate approval state. Decisions record reviewer name, server UTC time and optional comment in immutable revision history. With no app accounts, the name is explicitly reviewer-provided, not authenticated identity.

Approved topics omit the automatic AI-verification caution in student standalone HTML/PDF/DOCX and course-book chapters, including full notes and individual topics. Ordinary authored warning callouts, empty/failed-topic notices and unapproved topic warnings remain. No author/comment is exposed in student documents.

## Snapshot and ownership contract

- API/worker command is model-free, with base_revision, topic, approve/revoke, reviewer name (trimmed1..120chars) and optional comment (max2000chars). Server owns timestamp and content identity; clients cannot supply approval metadata through block edits. Reuse current API -> WorkerClient -> worker transaction -> staged render job path, with existing access rules/no new authentication system.
- Store backward-compatible optional teacher decision metadata on topics and appropriate revision provenance; new revision origin must distinguish approval/revocation from AI verification. Missing metadata in legacy notes means no approval. Reject invalid requests before mutation, keep revision/model/evidence compatibility.
- One shared pure topic-approval fingerprint/validity policy is used by mutation and every renderer. Identity binds ordered authored title/objectives/blocks/citations/evidence, document language/notation/terminology/relevant heading context, frozen source metadata used by the topic, and only referenced registered image assets. Exclude AI results/status/rounds/issues, approval itself, revision numbers and unrelated topic text/assets. Unknown/missing referenced source or image must fail closed. Bind to immutable saved evidence/source registry, not unrelated new course uploads. No hidden filesystem hashing on every GET.
- Approval applies only to an existing nonempty renderable saved topic (verified/unresolved), not failed/empty generation placeholders. Existing ready artifacts are not required; a previous render failure does not prevent a content decision. The teacher can approve unresolved/stale-AI text consciously; teacher judgment does not imply AI passed.
- Under existing run lock enforce base_revision and completed run; approve/revoke creates an immutable revision and stages HTML/PDF render intent before HEAD. No LLM. Parallel/stale commands yield409 and never apply to newer text. Persist decision even if rendering fails; normal render retry works, previous artifacts remain labelled with their actual revision. Word/book remain on-demand for that exact revision.
- Every commit validates active approvals against the resulting topic identity: content/formula/order/citation/figure/evidence or relevant source/context changes invalidate approval. Changes to other topics retain approval. Verify with identical authored content/evidence preserves approval even if AI metadata/findings change; F3 evidence refresh that appends evidence invalidates it.
- Restore only authored content; changed topics require new approval. Never copy/reactivate historical approval, including when restoring bytes that once had approval or a metadata-only approved snapshot. Unchanged topics retain current decision; revocation cannot be undone by restoring a snapshot. Historical approval and artifacts remain inspectable.
- Rendering independently requires decision==approved AND matching current snapshot fingerprint; a forged/stale approval cannot suppress warnings merely by being present. Same policy all four formats. Historical revision render uses that revision's decision, not HEAD.
- F1 authored/candidate identities remain byte compatible; optional new approval defaults must not invalidate legitimate pre-feature proposals. Approve/revoke revisions are not verification-only compatibility steps; older ready proposals crossing them conservatively conflict under current F1 policy.
